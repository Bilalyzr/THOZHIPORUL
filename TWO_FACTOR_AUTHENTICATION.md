## 1. Overview

Two-factor authentication adds a second verification step beyond the password.
After entering the correct email and password, the admin must also provide a
6-digit code generated by **Microsoft Authenticator** (or any TOTP app) on their phone.

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Factor 1    │     │  Factor 2    │     │   Result     │
│  Password    │ AND │  TOTP Code   │ ──> │  Authenticated│
│ "something   │     │ "something   │     │              │
│  you know"   │     │  you have"   │     │              │
└──────────────┘     └──────────────┘     └──────────────┘
```

**Why it matters:** Even if an attacker steals the admin's password (phishing,
breach, reuse), they cannot access the SIPCOT admin portal without the rotating
6-digit code from the admin's physical device.

## 2. How It Works

### 2.1 The Shared Secret

During enrollment, the server generates a random **hex secret** (20 random bytes →
40 hex chars). This secret is:

- Stored on the server in the `user_mfa` table (`secret_encrypted` column, base64-encoded)
- Transferred to the user's phone via a **QR code** containing an `otpauth://` URI (or manual entry)

Both sides now hold an identical copy of the secret. **They never communicate
again** — the code generation is entirely independent on each side.

### 2.2 Code Generation (TOTP Algorithm)

The 6-digit code is computed using the **RFC 6238** standard:

```
code = truncate(HMAC-SHA1(secret, current_time_window))

where:
  secret              = the shared hex secret (20 bytes)
  current_time_window = floor(unix_timestamp / 30)
```

Both the phone and server use the same `secret` + same `current_time_window`,
so they produce the **same 6-digit code** — without any network connection.

```
          SHARED SECRET
          ┌───────────┐
          │  hex (20B) │
          └─────┬─────┘
                │
     ┌──────────┴──────────┐
     ▼                     ▼
┌─────────┐           ┌─────────┐
│  PHONE   │           │ SERVER   │
│ (MS Auth)│           │ (Node.js)│
│          │           │          │
│ secret + │           │ secret + │
│ time     │           │ time     │
│    ↓     │           │    ↓     │
│ HMAC-SHA1│           │ HMAC-SHA1│
│    ↓     │           │    ↓     │
│ 148035   │           │ 148035   │  ← Same result ✓
└─────────┘           └─────────┘
```

### 2.3 Time Windows & Tolerance

- Codes rotate every **30 seconds**
- The server accepts a ±1 window tolerance, meaning it accepts:
  - The current code (this 30s window)
  - The previous code (last 30s window) — absorbs clock drift
  - The next code (next 30s window) — for codes typed just before rotation
- **Maximum acceptable window: ~90 seconds**

### 2.4 The Three Enrollment Phases

```
① SETUP                     ② VERIFY & ENABLE           ③ LOGIN (recurring)
┌──────────────────┐        ┌──────────────────┐        ┌──────────────────┐
│ POST /security/  │        │ POST /security/  │        │ POST /auth/login │
│   mfa/setup      │  scan  │   mfa/verify     │ verify │                  │
│                  │ ◀────▶ │                  │ ◀────▶ │ 1. Password ✓    │
│ Generate secret  │  QR    │ User types code  │        │ 2. Returns       │
│ Save to DB       │        │ Server verifies  │        │   mfa_required   │
│ enabled = FALSE  │        │ Match? enable=T  │        │                  │
│                  │        │                  │        │ POST /auth/      │
│ Returns: secret  │        │ Gate turns ON    │        │   verify-mfa     │
│ + otpauth URL    │        │                  │        │   → real token   │
└──────────────────┘        └──────────────────┘        └──────────────────┘
```

**Why enrollment is two-step:** If the user scans the QR but loses their phone
before confirming, they are **never locked out** — `enabled` stays `FALSE`
until they prove the code works. This is a deliberate safety design.

## 3. Architecture

### 3.1 Database Schema

The `user_mfa` table (from `schema_v3_enhancements.sql`, auto-applied at boot):

```sql
CREATE TABLE user_mfa (
    id                SERIAL PRIMARY KEY,
    user_id           INTEGER UNIQUE REFERENCES users(id) ON DELETE CASCADE,
    secret_encrypted  TEXT NOT NULL,          -- base64 of the hex secret
    enabled           BOOLEAN DEFAULT FALSE,
    backup_codes      TEXT[],
    enabled_at        TIMESTAMP
);
```

| Column | Purpose | Lifecycle |
|---|---|---|
| `secret_encrypted` | Base64 of the hex TOTP secret | Set by `POST /security/mfa/setup`; never returned after enable |
| `enabled` | Whether the 2FA gate is active | `FALSE` → flipped to `TRUE` by `POST /security/mfa/verify`; reset by `DELETE /security/mfa` |
| `backup_codes` | Reserved for future single-use recovery codes | Not yet populated |

### 3.2 Backend Components

| File | Responsibility |
|---|---|
| `backend/routes/auth.js` | Login gate: checks `user_mfa.enabled` for admins → returns `mfa_required` + challenge token. `POST /auth/verify-mfa` endpoint + TOTP `verifyTotp()` function + `POST /auth/impersonate/*` |
| `backend/routes/security.js` | MFA management: `GET /security/mfa/status`, `POST /security/mfa/setup` (generate secret + otpauth URL), `POST /security/mfa/verify` (confirm + enable), `DELETE /security/mfa` (disable) |
| `backend/schema_v3_enhancements.sql` | Creates the `user_mfa` table (auto-applied at boot) |

**Key implementation detail:** The TOTP verification is **native Node.js** using the built-in `crypto` module — **zero external dependencies** (no `pyotp`, no `otplib`, no `speakeasy`). The `verifyTotp()` function in `auth.js` implements RFC 6238 directly:

```javascript
function verifyTotp(secret, code) {
    const key = Buffer.from(secret, 'hex');
    const t = Math.floor(Date.now() / 1000);
    for (const step of [0, -1, 1]) {           // ±1 window tolerance
        const counter = Math.floor(t / 30) + step;
        const buf = Buffer.alloc(8);
        buf.writeBigUInt64BE(BigInt(counter));
        const hmac = crypto.createHmac('sha1', key).update(buf).digest();
        const offset = hmac[hmac.length - 1] & 0x0f;
        const bin = ((hmac[offset] & 0x7f) << 24) | (hmac[offset+1] << 16)
                   | (hmac[offset+2] << 8) | hmac[offset+3];
        const token = String(bin % 1000000).padStart(6, '0');
        if (token === code) return true;
    }
    return false;
}
```

### 3.3 Frontend Components

| File | Responsibility |
|---|---|
| `frontend/src/pages/Settings.jsx` | The 2FA setup card (3 states: disabled → verifying/QR → enabled). Calls `/security/mfa/*` endpoints. QR rendered via `api.qrserver.com` (no npm QR library needed). |
| `frontend/src/pages/Login.jsx` | Login flow: detects `mfa_required` response → shows centered 6-digit code entry → calls `/auth/verify-mfa` |

## 4. API Reference

All endpoints require authentication (`x-auth-token` header) except `/auth/login`.

### 4.1 `GET /api/security/mfa/status`

Check if 2FA is enabled for the current user. Used by the Settings page on load.

**Auth:** Required

**Response `200`:**
```json
{ "enabled": false }
```

---

### 4.2 `POST /api/security/mfa/setup`

Begin TOTP enrollment. Generates a fresh secret and returns it with the
`otpauth://` URI for QR rendering.

**Auth:** Required

**Request:** No body

**Response `200`:**
```json
{
  "secret": "E7EE890FB538DDA0A00E5730E75ABC3926679022",
  "otpauth_url": "otpauth://totp/THOZHIPORUL:admin@sipcot.com?secret=E7EE...&issuer=THOZHIPORUL&digits=6&period=30"
}
```

The `otpauth_url` is what gets rendered as the QR code for Microsoft Authenticator.

---

### 4.3 `POST /api/security/mfa/verify`

Finish enrollment by verifying a code from the user's authenticator app.
Flips `enabled` to `TRUE` and generates backup codes.

**Auth:** Required

**Request:**
```json
{ "code": "148035" }
```

**Response `200`:**
```json
{
  "msg": "MFA enabled",
  "backup_codes": ["a1b2c3d4", "e5f6g7h8", ...]
}
```

**Errors:**
- `400` — "Run MFA setup first" (no secret found)
- `401` — "Invalid verification code" (code didn't match)

---

### 4.4 `DELETE /api/security/mfa`

Turn 2FA off. Logs the disable action to the audit trail.

**Auth:** Required

**Response `200`:**
```json
{ "msg": "MFA disabled" }
```

---

### 4.5 `POST /api/auth/login` (with 2FA gate)

The login endpoint checks MFA status **for admins** after password verification.

**Request:**
```json
{
  "email": "admin@sipcot.com",
  "password": "password123"
}
```

**Flow:**
```
1. Verify password        → fail: 401 "Invalid credentials"
2. If role === 'admin':
   a. Check user_mfa.enabled
   b. If enabled → return mfa_required (NO session token issued)
   c. If not enabled → proceed normally (issue token)
3. Non-admin roles → proceed normally (MFA optional)
```

**Response when MFA is required (`200`):**
```json
{
  "mfa_required": true,
  "challenge_token": "eyJhbGciOiJIUzI1NiIs...",
  "email": "admin@sipcot.com",
  "msg": "Enter the 6-digit code from Microsoft Authenticator."
}
```

The `challenge_token` is a **short-lived 2-minute token** that identifies the
user for the `/verify-mfa` step. It does NOT grant access to any endpoint
except `/auth/verify-mfa`.

---

### 4.6 `POST /api/auth/verify-mfa`

Verify the 6-digit TOTP code and issue the real session token.

**Request:**
```json
{
  "challengeToken": "eyJhbGciOiJIUzI1NiIs...",
  "code": "148035"
}
```

**Response `200`:**
```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "role": "admin",
  "name": "Administrator",
  "email": "admin@sipcot.com"
}
```

**Errors:**
- `400` — "challengeToken and code required"
- `401` — "Challenge token expired or invalid"
- `401` — "Invalid verification code"
- `400` — "MFA not enabled for this account"

## 5. Frontend Integration

### 5.1 The Login Flow (with MFA challenge)

When an admin with MFA enabled logs in, the server returns `mfa_required: true`.
The frontend switches from the password form to a 6-digit code entry screen:

```jsx
// Login.jsx — conditional rendering based on mfaChallenge state
const handleLogin = async (e) => {
  const data = await authService.login(email, password);
  if (data.mfa_required) {
    setMfaChallenge({ challenge_token: data.challenge_token, email: data.email });
    return;  // ← show the 2FA code step instead of navigating
  }
  // ... normal redirect
};

const handleVerifyMfa = async (e) => {
  const data = await authService.verifyMfa({
    challengeToken: mfaChallenge.challenge_token,
    code: mfaCode
  });
  if (data.token) {
    localStorage.setItem('token', data.token);
    navigate('/admin-dashboard');
  }
};
```

### 5.2 The Settings Card (3 states)

`Settings.jsx` renders the 2FA section with three states:

| State | Trigger | What Shows |
|---|---|---|
| **Disabled** | `mfaStatus === 'idle'` | Navy card with `DISABLED` chip + "Set Up 2FA Now" button |
| **Verifying** | After `/mfa/setup` call | QR code (via `api.qrserver.com`) + manual key + 6-digit entry + "Verify & Enable" |
| **Enabled** | `mfaStatus === 'enabled'` | Navy card with `ENABLED` chip + green success alert + "Disable 2FA" button |

The QR code renders as:
```jsx
<img src={`https://api.qrserver.com/v1/create-qr-code/?size=220x220&data=${encodeURIComponent(mfaOtpauth)}`} />
```

No client-side QR library needed — the QR is generated server-side by the public API.

### 5.3 API Client Functions

```javascript
// frontend/src/services/api.js
authService.verifyMfa = (data) => api.post('/auth/verify-mfa', data);

// Settings.jsx uses raw fetch() calls to:
//   GET  /api/security/mfa/status    → { enabled: true/false }
//   POST /api/security/mfa/setup     → { secret, otpauth_url }
//   POST /api/security/mfa/verify    → { msg, backup_codes }
//   DELETE /api/security/mfa         → { msg }
```

## 6. Setup Guide (End Users)

### For admins (2FA required)

1. Log in to the admin portal with your email + password
2. Go to **Settings** (sidebar → Account → Settings)
3. Under **Two-Factor Authentication**, click **"Set Up 2FA Now"**
4. A **QR code** appears. Open **Microsoft Authenticator**:
   - Tap **+ Add account** → **Other account** (the "phone" icon)
   - Point your phone camera at the QR code
   - The app adds a "THOZHIPORUL" entry showing a rotating 6-digit code
5. Type the 6-digit code shown in the app into the **"6-Digit Code"** field
6. Click **"Verify & Enable"**
7. Done! The card now shows **ENABLED** with a green chip

**At next login:**
1. Enter your email + password → click "Sign In"
2. The screen switches to a **6-digit code entry** (large centered input)
3. Open Microsoft Authenticator → read the current code → type it
4. Click **"Verify & Sign In"** → you're in

**If you can't scan the QR:** Tap "enter code manually" in your app and type
the hex secret shown below the QR (labelled "Manual key").

## 7. Setup Guide (Administrators)

### 7.1 Checking 2FA status for all users

```sql
SELECT u.email, u.role,
       CASE WHEN m.enabled THEN '✅ ON' ELSE '❌ OFF' END AS two_factor
  FROM users u
  LEFT JOIN user_mfa m ON m.user_id = u.id
 WHERE u.role = 'admin';
```

### 7.2 Disabling 2FA for a locked-out admin (emergency)

If an admin loses their authenticator device and can't log in, a database
admin can reset 2FA:

```sql
-- Temporarily disable MFA so the admin can log in and re-enroll
UPDATE user_mfa SET enabled = FALSE WHERE user_id = (
    SELECT id FROM users WHERE email = 'admin@sipcot.com'
);
```

The admin should then immediately go to **Settings → Set Up 2FA Now** to
re-enroll with a new device.

### 7.3 Audit trail

All MFA-related actions are logged to the `audit_logs` table:

| Action | Audit entry |
|---|---|
| Enable 2FA | `Enabled MFA` (severity: warning) |
| Disable 2FA | `Disabled MFA` (severity: warning) |
| Login with 2FA | `USER_LOGIN (2FA verified) — admin portal` (severity: warning) |

## 8. Role-Based Enforcement

The login gate in `backend/routes/auth.js` applies MFA **only for admins**:

```javascript
// After password verification succeeds:
if (user.role === 'admin') {
    const mfaRow = await db.query('SELECT enabled FROM user_mfa WHERE user_id = $1', [user.id]);
    if (mfaRow.rows.length && mfaRow.rows[0].enabled) {
        // Issue a 2-minute challenge token, return mfa_required
        return res.json({
            mfa_required: true,
            challenge_token: challengeToken,
            msg: 'Enter the 6-digit code from Microsoft Authenticator.'
        });
    }
}
// Otherwise proceed normally (issue the real session token)
```

| Role | 2FA Policy | If `enabled = false` | If `enabled = true` |
|---|---|---|---|
| `admin` | **Available, enforced when enabled** | Login works normally | Login requires TOTP code |
| `govt` | Optional (not enforced) | Login works normally | Login works normally (MFA setup available but not gated) |
| `industry` | Optional (not enforced) | Login works normally | Login works normally (MFA setup available but not gated) |

> **Note:** To make 2FA **mandatory** for admins (hard gate — can't log in at all without it),
> the admin first enables it via Settings. Once enabled, every subsequent login requires the code.

## 9. Operational Procedures

### 9.1 Resetting a user's 2FA (admin operation)

If an admin loses their phone, a database admin can reset their 2FA:

```sql
-- Option A: Disable MFA (admin can log in, then re-enroll via Settings)
UPDATE user_mfa SET enabled = FALSE WHERE user_id = (
    SELECT id FROM users WHERE email = 'admin@sipcot.com'
);
```

After resetting, the admin logs in normally (no code required), goes to
**Settings → Set Up 2FA Now**, scans a new QR, and re-enables.

### 9.2 Changing to a new phone

1. In **Settings**, click **Disable 2FA** (requires no code — already authenticated)
2. Click **Set Up 2FA Now** → scan the new QR with the new phone
3. Verify the code → re-enabled

### 9.3 Verifying the system is working

```bash
# Check if an admin has MFA enabled
curl -s http://localhost:5001/api/security/mfa/status \
  -H "x-auth-token: $TOKEN"
# Expected: {"enabled":true}

# Try logging in as an MFA-enabled admin (should return mfa_required, NOT a token)
curl -s -X POST http://localhost:5001/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@sipcot.com","password":"CORRECT_PASSWORD"}'
# Expected: {"mfa_required":true,"challenge_token":"eyJ..."}
```

## 10. Troubleshooting

### "Invalid verification code" at setup or login
- **Cause:** The code doesn't match what the server expects.
- **Check:**
  1. Are you entering the code for the **THOZHIPORUL** account in your authenticator?
  2. Is your phone's clock accurate? (Settings → Date & Time → Automatic)
  3. Has the code expired? (wait for a fresh one — they rotate every 30s)
  4. Was the secret entered correctly during manual setup?
  5. Try waiting for a new code at the start of a 30-second window

### Login shows the 2FA screen unexpectedly
- **Cause:** MFA was enabled (possibly by you in Settings earlier).
- **Fix:** Enter the code from Microsoft Authenticator. Or ask a DB admin to disable MFA (Section 9.1).

### QR code doesn't display in Settings
- **Cause:** The QR image fails to load (network issue with `api.qrserver.com`).
- **Fix:** Use the **manual key** shown below the QR — type it into Microsoft Authenticator → Add → Other → Enter manually.

### "Run MFA setup first"
- **Cause:** You clicked "Verify & Enable" without first clicking "Set Up 2FA Now".
- **Fix:** Click "Set Up 2FA Now" first → scan QR → then enter code → Verify.

### Lost phone / can't generate codes
- **Cause:** The authenticator device is lost/reset.
- **Fix:** Ask a database admin to reset via SQL (Section 9.1), then re-enroll.

## 11. Security Considerations

### Strengths
- ✅ Codes expire every 30 seconds (can't be replayed)
- ✅ Secret never transmitted during login (only the derived code)
- ✅ Works offline (no phone network/internet required for code generation)
- ✅ Challenge token expires in 2 minutes (can't be reused)
- ✅ Native crypto (no third-party library = smaller attack surface)
- ✅ RFC 6238 compliant (industry standard TOTP)
- ✅ All enable/disable/login events audit-logged
- ✅ Microsoft Authenticator compatible (the govt-mandated authenticator)

### Limitations & Recommendations

| Issue | Status | Recommendation |
|---|---|---|
| No backup/recovery codes | ❌ Not yet surfaced | The table has a `backup_codes` column — generate + display them on enable |
| Secret stored base64 (not encrypted) | ⚠️ Current | Encrypt `secret_encrypted` with a KMS key for production |
| No rate limiting on OTP attempts | ⚠️ Current | Add per-account rate limiting (e.g., 5 attempts / 5 min) on `/verify-mfa` |
| QR via external API | ⚠️ Current | Generate QR server-side with a Node QR library for offline deployments |
| `±1` window tolerance | ✅ Current | Standard; consider tightening to `0` for high-security deployments |
| MFA for govt/industry roles | Optional | Currently admin-only enforcement; can extend to govt easily |
